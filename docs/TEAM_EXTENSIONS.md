# MC 陪玩 Agent：五个扩展方向自选

可转发给组员的 [Word 档案](handbook/MC陪玩Agent_组员扩展档案_20261025.docx) 已包含五个方向、共同交付标准与认领表。

共同目标：玩家能够感知“这个 NPC 正在和我一起玩”，并能用真实游戏数据解释改进在哪里。每人认领一个主方向，先完成一个可以演示的最小闭环；不要把语音、视觉大模型、RL、跨游戏迁移一起加进来。

下文指标是**拟定验收目标**，不是已取得的结果。先跑小规模预实验，再冻结任务、预算与判据；若要调整目标，记录原因，不能看完结果才改成功定义。

## 方向总览

| 方向 | 玩家看到什么 | 主要能力 | 预计首次闭环 | 建议认领 |
|---|---|---|---|---|
| A 玩家偏好与自适应协作 | 记得确认过的偏好，并按当前任务调整帮助 | 数据建模、检索、Java 持久化、实验 | 1–2周 | 负责人或偏算法的成员 |
| B 生存补给与采集探索 | 缺什么补什么，先查共享物资，再合理探索 | Lua/Java 技能、游戏感知、失败处理 | 1–2周 | 1人 |
| C 执行经验与失败恢复 | 不在同一个失败上反复撞墙 | 结构化回执、经验检索、LLM 工程 | 1–2周 | 1人 |
| D 陪玩互动与共同目标 | 能接话、配合、庆祝，也会及时收手 | 交互设计、事件处理、技能组合 | 1–2周 | 1人 |
| E 可复现实验与状态观测 | 能回看“为什么这么做、最后做成没有” | 游戏测试、日志、可视化、统计 | 1–2周 | 可替换 B/C/D 之一 |

“首次闭环”只估计第一份可演示结果，不代表方向全部完成。四人团队建议负责人做集成并推进 A，其余三人从 B/C/D/E 中各选一个；E 的共同记录格式由负责人先协调。

## A. 玩家偏好与自适应协作

**问题。** 同一句“帮我准备建材”，有的玩家希望 NPC 主动采集，有的希望只汇报缺口。当前确认式记忆可以作为基线，但不能把一次靠近建筑或捡到物品就当成稳定偏好。

**最小闭环。** 只研究“主动帮助程度”和“偏好的建筑材料”两个维度。记录证据来源、时间、适用任务、是否确认；将推测与确认信息分开。玩家可以查看、纠正、撤销；规划前检索最多若干条真正相关信息，遵从当前明确请求。

**代码入口。** `plugins/sceneadapt/.../PlayerStore.java`、`PlayerApi.java`、`NumenSceneAdapt.java`，以及 `PlayerStoreTest`、`PlayerApiTest`。已有 `sceneadapt.player.context()`、记忆提议与确认机制，先复用。原生长对话压缩与任务执行机制不重写。

**可做的方法。** 显式反馈沿用 Beta 统计，`p=(a+h)/(a+b+h+u)`；当前基线先验为 `a=b=2`，h/u 为明确“有帮助/无帮助”反馈，不能把未反馈算成反对。扩展时可比较“只用最近确认记录”和“任务相关检索+时间衰减”；关联系数只是偏好证据，不等于行为授权。不需要先训练神经网络。

**实验。** 三组预先写定偏好情形，每组至少10个请求，与不注入玩家偏好、只注入全部记忆两个基线比较。相同世界/库存、相同模型与预算，记录是否正确遵从“当前请求优先于历史偏好”。合成玩家脚本仅用于工程回归，另做真实玩家的短体验，不能混为一类样本。

**验收目标。** 相关确认信息召回命中率至少80%；明确纠正后的下一轮遵从率至少90%；跨玩家串读为0；撤销/清除生效的确定性用例全通过。报告交互满意度时给原始人数和问题，不凭3个人的体验宣称普遍有效。

**交付。** 玩家信息结构、检索接口、撤销演示、对照 CSV/JSON 与2分钟录像。创新体现在“有证据、可纠正、情境相关的帮助”，不是只换一段系统提示词。

## B. 生存补给与采集探索技能包

**问题。** NPC 经常缺木材/食物/火把，却重复扫描或采集已经建好的房子。目标是让它与玩家共享补给任务，既能行动，也能明确解释目前做不了什么。

**最小闭环。** 只选一种任务：食物补给、火把准备或建筑木材补给。流程为需求检查→已授权共享库存→可见自然资源→有界探索→采集/合成→真实库存验收。每次探索有步数/时间预算，失败返回可用的上下文，不建立一个锁死 Agent 的全局任务状态机。

**代码入口。** 现有 `numen/.../skills/numen/`、原生 `numen.inv`/`numen.work`/`numen.move` 等接口及其帮助；`ArchitectureMaterials.java` 与 `CooperationApi.java` 可作为材料观察/显式批次的例子。先用 Lua 技能组合，只有缺少稳定原子能力才增加 Java API。

**感知边界。** 允许使用实际可观察的已加载信息；未知区块仍是未知，不读取地下遮挡矿石作路线答案。不将生成结构或保护建筑当成自然矿源，不打开未经授权的私人箱子，不用管理员命令送资源。

**实验。** 固定10个可重建起点，分别设置“共享箱已有”“附近可见”“需要探索”三类情形，共30次；新方案与现有技能在同一模型、相同起点/库存和预算下对照。共享箱存在时，额外记录是否还无意义外出。

**验收目标。** 在明确资源可得的预定义情形中至少8/10次于预算内实际补齐；成功以库存和原料消耗核验。对不可得情形100%给出不足/预算耗尽回执，不能反复无界重试。破坏受保护建筑、虚构物资为0。死亡、路程、耗时、LLM 调用数和玩家救援次数全部记录，不能只报成功样例。

**交付。** 一个可开关技能、一个真实游戏补给演示、三类场景重建说明、对照结果。后续可以扩到农作/照明，但先把一种需求做稳。

## C. 执行经验检索与失败恢复

**问题。** “无路可达”“缺少工具”“材料不足”是不同问题。让 Agent 复用曾经有效的处置经验，而不是每次失败都从头猜、或者原样重试。

**最小闭环。** 只处理两类真实错误。将一次执行记录为 `{任务语义, 前置条件摘要, 工具, 参数摘要, 结果, 错误类型, 实际变化, 后续修正, 验证结论}`。先按错误类型与环境条件过滤，再做 BM25/标签检索，最多返回3条。把成功、失败、尚未验证的经验分开，不把模型的自我表扬当成功标签。

**代码入口。** `numen-api/.../api/task/TaskResult.java`、`api/agent/request/TaskReport.java` 和 `docs/shell.md` 的回执结构；先通过公开插件/工具入口接入记录与查询。核心任务结果协议如需变更，提交负责人评审。`e2e/.../FakeModel.java` 与 `FakeModelSteeringTest.java` 可验证新输入与回执关系。

**方法。** 对照“无经验”和“注入全部历史”；主方案只检索任务/错误/条件相似的少量经历。先用可解释检索，不急着引入向量库。经历中的文字是数据，不得带入高优先级指令；不保存 Key 或完整私人聊天，也不自动执行经验里附带的代码。每次使用仍要经过当前权限与感知。

**实验。** 训练集只用于整理经验，不训练模型权重；按场景种子/障碍布局划分开发集与留出集。每类至少10个留出场景；固定模型、步数/时间和token预算，防止把原样重放记忆当泛化。

**验收目标。** 留出集报告真实任务成功率与“相同失败连续重复次数”的配对差异；期望后者下降至少30%，同时成功率不下降超过预先约定的5个百分点。达不到也如实报告，不能只展示检索成功。错误经验可撤销，跨玩家隔离和未授权动作拒绝的回归全通过。

**交付。** 经验记录/查询接口、证据可追溯样例、留出集、对照结果与失败复盘。这里是经验工程，不把它写成 RL 或声称更新了模型权重。

## D. 陪玩互动与共同目标表达

**问题。** 主动性不足像工具，过度主动又打扰玩家。研究“何时表达、表达什么、玩家拒绝后怎样调整”，让 NPC 的陪玩更自然。

**最小闭环。** 三类情形选两类：共同目标开始时确认一句；观察到玩家需要帮助时提出一次建议；任务验证完成后邀请庆祝。采用明确冷却/去重，交互可开关。玩家说“先别打扰”后能停止主动话题，玩家换目标时旧目标不再牵引行动。

**代码入口。** `SocialInteraction.java`、`SocialTask.java`、`social_interaction/SKILL.md`，以及原生收件箱/目标接口。显示扩展在 `CooperationPanel.java`，它仍只读；不能偷偷用浮窗接管规划。已有H回应与Shift+H婉拒，不新增强制动作窗口。

**方法。** 轻量事件条件决定“是否值得问”，LLM负责语义与表达；不为每个时间刻发模型请求。依据已确认偏好控制打扰程度，优先复用A的契约。所有邀请到期、拒绝、危险中断均可观察。

**实验。** 至少10条固定事件序列做去重/冷却/中断回归，再邀请3–5位自愿体验者完成相同的5分钟任务。比较关闭主动表达与开启表达；条件顺序交错，避免总把改进版放后面。记录打断次数、有效帮助采纳、明确拒绝后再次打扰、主观“配合感/烦扰感”。小样本只作探索性描述。

**验收目标。** 同一事件不重复播报；明确拒绝后冷却内重复邀请为0；互动前后生命值不因庆祝下降；新目标/取消请求能够抵达唯一规划器。真实玩家结论保留反例，不只截取夸奖。

**交付。** 一个可开关互动技能、交互时序图、去重测试、体验记录与短演示。不要靠攻击玩家表达完成，也不要声称现有模型一定支持专属动画。

## E. 可复现实验与 Agent 状态观测

**问题。** “感觉更聪明”难以交付。建立能同时解释工程正确性和真实模型效果的实验工具，避免聊天说成功、游戏里却没完成。

**最小闭环。** 为一个现有协作任务记录时间线：玩家请求→感知摘要→规划/工具→实际回执→库存/方块验收→终止原因。统一run_id、代码提交、模型标识、世界种子、起点、预算和测试条件，Key与私人聊天脱敏。先做本地HTML/JSON报告，不重写游戏UI。

**代码入口。** `e2e/src/e2eTest/java/.../ArchitectureTest.java`、`GeneratedArchitectureTest.java`、`LiveArchitectureProbe.java`，以及 `bench`、`docs/bench.md`。真实模型探针是显式触发的付费实验，不能在普通CI自动使用成员Key。

**对照设计。** 每组至少10个固定重建场景，随机/交错运行基线与改进。每次开始恢复同一状态；固定模型、温度、预算与资源权限。成功以预先定义的世界检查为准，超时、死亡、人工干预都作为结果保留。重试是一次新尝试，不能覆盖旧失败。

**指标。** 成功率 `成功次数/总尝试数`；实际完成时长；同类错误重复数；玩家救援次数；动作/LLM调用量；可取得时报告token消耗。对成功率给Wilson区间，对耗时至少给中位数、分位数和全部原始值；10次样本不能推出普遍性能优势。

**验收目标。** 每次运行都有完整终止原因；已知失败不能被标成功；同一个模拟脚本重复3次得到相同语义结论（不要求时间戳相同）；报告中100%区分模拟模型与真实模型。任一组员能按说明重建并复核至少一个场景。

**交付。** 一个通用结果结构、记录/报告工具、基线数据与失败案例。无需引入新模型，价值在于形成能让其他四个方向可信迭代的实验基础。

## 共同时间安排与完成标准

| 阶段 | 每人做什么 | 负责人做什么 |
|---|---|---|
| 第1周 | 跑通构建；认领；提交1页接口/实验设计；复现一个当前缺陷 | 固定基线、评审接口、约定共同结果字段 |
| 第2周 | 最小功能、单一场景、至少一个正确性测试与短演示 | 逐个接入，检查是否另开大脑或绕过权限 |
| 第3–4周 | 完成对照场景、记录失败、做一轮改进 | 固定评测条件，安排交叉复现 |
| 第5周及以后 | 按真实结果决定深入哪一点，不盲目加功能 | 选择可展示的集成主线，保留课程缓冲 |

这是从本次认领开始的相对推进节奏，不重置原课程的十周截止时间；负责人应按剩余周数压缩，至少保留2–3周集成/课程实践缓冲。
